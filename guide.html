How to write a README for GitHub

A README is the front page of a repository. This guide covers the sections worth including, the Markdown you need, and the mistakes that make a README hard to use.

What a README is for

When someone lands on your repository, the README is rendered directly below the file list. In practice it answers four questions: what is this, why would I use it, how do I run it, and who made it. If a visitor cannot answer those in about thirty seconds, the project looks harder to adopt than it is. A README is not marketing copy; it is documentation with a job to do.

The sections most repositories need

Not every project needs all of these. Start with the first four and add the rest as the project grows.

Title and description

The project name and one or two sentences explaining what it does and who it is for. This is the part most people read.

Installation

The exact commands to get it running, in a fenced code block. Copy and paste should work.

Usage

A short, realistic example. One working snippet beats a paragraph of explanation.

Licence

State the licence and link to the file. Without one, others cannot legally reuse the code.

Features

A short list of what the project does well. Useful for scanning.

Screenshots

For anything with a user interface, an image explains more than text.

Contributing

How to report a bug or open a pull request, and what you expect from contributors.

FAQ

Answers to questions you are asked repeatedly. Keep each one short.

The Markdown you actually need

GitHub uses GitHub Flavoured Markdown. A small subset covers almost everything a README needs.

What you wantWhat to write
Heading## Installation
Bold and italic**bold** and _italic_
Bullet list- item
Numbered list1. item
Task list- [x] done
Link[text](https://example.com)
Image![alt text](image.png)
Inline code`npm install`
Code blockThree backticks, the language, then your code
TablePipe-separated cells with a --- separator row
Collapsible sectionA details element with a summary

A fenced code block with the language named after the opening backticks gets syntax highlighting. Use bash for shell commands, javascript for JavaScript, and so on.

Adding badges

Badges are small images that state a fact about the project: the licence, the latest release, whether the build passes. Most projects use Shields.io, which serves an image from a URL, so a badge is just an image written in Markdown.

Dynamic badges read live data from GitHub, npm or PyPI. The build status badge, for example, points at a workflow file in your repository and updates whenever that workflow runs. Keep the set small and relevant; a row of twenty badges is harder to read than four.

Profile READMEs

GitHub renders a README from a repository named exactly after your username on your profile page. It is a good place for a short introduction, the technologies you work with, and links to your work. Statistics cards from community projects can show your contribution graph, top languages and streak. Treat it as an introduction, not a wall of badges.

Common mistakes

  • No installation instructions. The most common gap. If a reader cannot run it, they will move on.
  • Assuming context. Naming a folder or a service without explaining it makes the README unreadable to newcomers.
  • Broken relative links. Links to files in the repository must match the real path and capitalisation.
  • Images that do not load. Check that the URL is public and permanent; links to private storage break for everyone else.
  • Stale content. A README describing a previous version is worse than a short one that is accurate.
  • No licence. Without one, others cannot legally reuse the code.

Questions

How long should a README be?

As long as it needs to be and no longer. A small library can be covered in a screen or two. Put the essential information first and the details below it.

Should the README be in one language or several?

Write it in the language your users are most likely to read. If you need several, keep each translation in its own file and link between them.

Where does the README file go?

In the root of the repository, named README.md. GitHub renders it on the repository home page.

Can I use HTML inside a README?

Yes. GitHub allows a subset of HTML, which is how centred headings, aligned images and collapsible sections are done.
